# rezel-lr

Static-table LR runtime for parsers generated by Rezel.

## When to depend on this crate

Most applications should start with a `rezel-lang-*` crate. Add a direct
dependency on `rezel-lr` when you are:

- publishing generated parser code;
- implementing an external tokenizer, contextual token source, or
  specializer;
- configuring a generated parser's top rule, dialect, strictness, or resource
  limits.

Generated parser crates should use the same `rezel-lr` and `rezel-common`
versions as the generator that emitted them.

## Runtime model

Generated code defines an immutable `Language` containing LR states, compact
action and goto tables, token automata, node metadata, and optional external
hooks. `LRParser` shares that static language data while keeping parser
configuration owned:

```rust
use rezel_lr::LRParser;

fn strict(parser: LRParser) -> LRParser {
    parser.with_strict(true)
}
```

`ExternalTokenizer` receives an `InputStream` over UTF-16 code units, matching
Lezer grammar semantics. Public source positions remain UTF-8 byte offsets
represented by `rezel_common::TextSize`.

`ParseLimits` bounds actions, active GLR stacks, stack depth, buffered records,
and recovery work for untrusted input.

## Current limits

Incremental fragments, reused-node actions, and cross-parse context reuse are
not currently supported. Parser tables are supplied as generated Rust static
data rather than deserialized JavaScript parser images.
