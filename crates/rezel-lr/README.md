# rezel-lr

Static-table LR/GLR runtime for parsers generated by Rezel.

## Role in the system

A generated `Language` combines immutable grammar structure with parse tables,
token automata, node metadata, dialects, and statically linked external hooks.
`LRParser` borrows that language and owns cheap configuration:

```rust
use rezel_lr::LRParser;

fn strict(parser: LRParser) -> LRParser {
    parser.with_strict(true)
}
```

Applications normally use a `rezel-lang-*` facade. Depend on `rezel-lr`
directly when publishing generated language code, implementing an external
tokenizer/context/specializer, or configuring low-level parser behavior. The
generator, runtime, common crate, and generated package must use compatible
versions.

## Parser tables

`rezel-generator` emits parser glue and two binary table representations:
little-endian and big-endian. Generated code selects the target's native
endianness at compile time and validates the borrowed layout with `zerocopy`.
Parser construction does not deserialize a portable image or allocate another
owned copy of the tables. It builds compact auxiliary indexes for hot action,
goto, and token lookup; language facades normally construct and cache that
immutable parser once.

The engine executes LR actions, creates explicitly allowed GLR branches, merges
compatible stacks, and builds compact CST buffers. Recovering mode searches
bounded repair paths and records syntax errors in the tree. Strict mode rejects
syntax errors instead.

## Tokenization and context

`InputStream` exposes logical `CodePoint` values while all positions and token
ranges remain original UTF-8 byte offsets. Ordinary source yields Unicode
scalar values; a language-owned lexical view may deliberately present
translated code points.

Generated token DFAs and local token groups share the runtime with:

- `ExternalTokenizer` for bounded parser-aware lexical decisions, optionally
  guarded by a conservative first-code-point set;
- `ContextTracker` for immutable state across shifts and reductions;
- generated or external specializers for base-token reclassification;
- dialect selection and parser-state token filtering.

External code receives validated stream operations and the current `Stack`.
It remains responsible for deterministic progress and for reporting malformed
language input as a parser error. An external tokenizer may also declare a
conservative `ExternalTokenizerStart` set. The runtime then skips its callback
when the next logical code point cannot start one of its tokens. This is only a
performance filter: the callback still makes the parser-aware decision, and
the declared set must include every code point and end-of-input position where
the callback can accept or return an error. Only a guaranteed decline may be
filtered out.

## Configuration and bounds

`LRParser` can select a top rule and dialect, enable strict parsing, replace the
generated context tracker, add parse wrappers, configure tree buffering, and
set `ParseLimits`.

Limits bound action count, active GLR stacks, stack depth, buffered records,
and recovery actions. External tokenizers must apply their own proportional or
explicit scan bounds. Fatal input, configuration, and resource errors remain
distinct from recoverable syntax.

`PartialParse` can advance one parse in steps or stop at a position. Reusing
fragments between separate source versions is not currently implemented.
